## Known governance-doc inconsistency (auth-setup audit finding)
BEHAVIORAL_CONTRACTS.md's "Permissions model" paragraph and ARCHITECTURE.md's RLS section both describe `user_id`-scoped Postgres RLS policies on `gap_audit_runs` and `artifact_health_scores`. This does not match the schema actually built in prompt 1 and confirmed authoritative by two other governance documents:
- SCHEMA_REGISTRY.md: both tables list `RLS: disabled`, `Tenant-scoped: no`, and neither has a `user_id` column.
- BEHAVIORAL_CONTRACTS.md's own "API Contracts" conventions (a few paragraphs above the Permissions model): "All database access to gap_audit_runs and artifact_health_scores uses the Build Memory SQLite file at ~/.forge/forge_memory.db ... not Supabase Postgres."
- TESTING.md Law 1: "This project is SINGLE-TENANT (no company_id/tenant_id columns, no RLS policies -- SQLite file permissions provide isolation)."

SQLite has no RLS mechanism, so this prompt did not add a `user_id` column or RLS policies to those two tables (doing so would also fail Sentinel's schema-drift check against SCHEMA_REGISTRY.md, which is read-only during Phase 3). Authorization for those tables is instead enforced exactly as the Permissions model paragraph's own closing sentence describes: "Permission checks are enforced in code at the API layer, not solely by RLS" — i.e. `lib/supabase/route-auth.ts#requireOperatorSession()`, which every future route handler in api-audit/api-resurrect/api-health must call. The one table that genuinely lives in Postgres and does carry RLS is `profiles` (auth.uid() = id), added this prompt per ARCHITECTURE.md's `profiles` spec, which is internally consistent with BEHAVIORAL_CONTRACTS.md's Middleware section.

Also: middleware.ts and route-auth.ts use `supabase.auth.getUser()` rather than the literal `getSession()` named in BEHAVIORAL_CONTRACTS.md's Middleware/Flows prose. This is an intentional, security-motivated substitution: `getSession()` decodes the session cookie locally without revalidating it against the Supabase Auth server, while `getUser()` does revalidate on every call — the standard Supabase SSR guidance for exactly this server-side context (middleware, route handlers). The externally observable behavior described by the contract (redirect to /login on invalid session; 401 JSON for /api/*) is unchanged.
