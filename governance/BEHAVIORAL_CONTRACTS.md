## API Contracts
#### Conventions
- All routes are prefixed /api and implemented as Next.js 14 App Router Route Handlers under src/app/api/.
- Authentication is enforced via Supabase Auth session on every authRequired route; the session is read server-side from cookies using createServerComponentClient -- never from the request body.
- machine_id is derived server-side from the host environment (os.hostname() + a stable UUID seeded at first run and persisted to ~/.forge/machine_id) and injected into every gap_audit_runs and artifact_health_scores insert; it is never accepted from the client.
- All database access to gap_audit_runs and artifact_health_scores uses the Build Memory SQLite file at ~/.forge/forge_memory.db via the ForgeLearning database.ts client -- not Supabase Postgres.
- The GapAuditor pipeline (POST /api/audit/run) is always invoked as a background task using a server-side async job; the HTTP response returns immediately with auditRunId and status 'running', and the client polls GET /api/audit/run/:auditRunId for completion.
- RegenerationEngine writes governance docs only when regenerationTier is AUTO and no CRITICAL gap exists on the artifact, and only when the project is not in Phase 3 (R3). A Phase 3 detection check runs before any write.
- HumanGateEvaluator routes are non-bypassable: no environment variable, feature flag, or request parameter can skip the gate for CRITICAL-severity gaps (R4 / F23).
- All ForgeRetrofit scanning is invoked via the existing runScan / runRetrofitPipeline entrypoints; no new filesystem-walk code is introduced under src/resurrection/ (R5).
- composite_score = (completeness_score * 0.5) + (freshness_score * 0.25) + (consistency_score * 0.25), rounded to three decimal places, computed server-side before insert.
- health_score_before on gap_audit_runs equals the arithmetic mean of all nine artifacts' composite_score at audit start (null if no prior scores exist for the project); health_score_after is recomputed after all AUTO regenerations complete.
- halt_point_reference is stored as a JSON TEXT blob in gap_audit_runs and always includes the fields {buildRunId, featureBranch, promptIndex, promptName, failingCheck, subStepIndex, subStepName}; absent facts are stored as null, never fabricated (R2).
- All API responses use JSON with Content-Type application/json and include a top-level 'error' field on non-2xx responses with fields {status, code, description}.
- Pagination uses limit/offset semantics on all list endpoints; default limit is 20 except artifact-scores which defaults to 50.
- All timestamps are ISO 8601 UTC strings in API responses.
- TypeScript strict mode is enforced across all route handlers and shared types are defined in src/types/resurrection.ts.
- The /api/resurrect/resume endpoint writes a status update to gap_audit_runs (resumeInitiatedAt timestamp) but does not create a new row; the audit run is the canonical record.
- No route accepts company_id or tenant_id -- this is a single-operator, single-machine system (PRD §Non-Goals, SCHEMA_ADDITIONS §7).

  1. Middleware redirects to /login (never renders a default or wrong-role page)
  1. User submits credentials on /login page

  1. On success: Supabase sets httpOnly session cookie, server reads role from profiles table
  1. On role-fetch failure: redirect to /login -- never render a default or wrong-role page (Iron Law 4)
  1. On success with valid role: redirect to / (dashboard)
- **Authenticated API Request**
  1. Client sends request to any /api/* route with session cookie
  1. Middleware validates Supabase session JWT
  1. On invalid/expired JWT: return 401 JSON, do not redirect (API contract)
  1. On valid JWT: middleware reads role from profiles.role
  1. On role-fetch failure: return 401 JSON, never infer a default role

- **Resurrect Resume Flow**
  1. Operator navigates to /resurrect
  1. Middleware enforces operator role; on failure redirects to /login

- **Session Expiry and Refresh**
  1. Supabase session approaches expiry
  1. Supabase client-side SDK silently refreshes token if refresh token is valid
  1. On refresh failure: middleware on next navigation detects invalid session
  1. Middleware redirects page routes to /login; API routes return 401
  1. User re-authenticates; session restored

#### Middleware
Next.js middleware at src/middleware.ts intercepts every request. For page routes (non-/api, non-/_next, non-/login, non-/favicon): call supabase.auth.getSession(); on null session redirect to /login with the original pathname as a `next` query param -- never render a default or wrong-role page (Iron Law 4). On valid session, fetch profiles.role for the authenticated user id; on any fetch error or missing role redirect to /login immediately -- never infer a default role. Attach role to request headers (x-user-role) for downstream Server Components. For /api/* routes: call supabase.auth.getSession(); on null or invalid session return NextResponse.json({error:'Unauthorized'},{status:401}) -- no redirect. On valid session fetch profiles.role; on fetch failure return 401 JSON. Attach role to request headers. The /login page and /api/auth/* routes are always public and bypass all checks. Static assets (/_next/static, /favicon.ico) bypass all checks. Middleware uses the Supabase SSR client (@supabase/ssr createServerClient) with cookies() from next/headers to avoid session leakage between requests.

#### Multi-tenancy
Single-tenant. No companies table, no tenant_id, no org scoping, no RLS tenant policies. The application is scoped to one operator on one local machine. All data in gap_audit_runs and artifact_health_scores is globally readable by the authenticated operator. The only scoping columns are machine_id (identifying the local machine per SCHEMA_ADDITIONS §0 / Iron Law R6) and user_id (foreign key to auth.users for the single Supabase Auth user). Supabase RLS policies are per-user: a row is accessible if auth.uid() = user_id. There is no multi-user sharing, no invite flow, and no team-level access control.

#### Permissions model
Flat single-role model. There is exactly one application role: operator. All authenticated users (in practice exactly one) hold the operator role, stored in a profiles table (columns: id uuid PK references auth.users(id), role text NOT NULL DEFAULT 'operator', created_at timestamptz NOT NULL DEFAULT now()). RLS on gap_audit_runs: SELECT/INSERT/UPDATE/DELETE allowed when auth.uid() = user_id. RLS on artifact_health_scores: SELECT/INSERT/UPDATE/DELETE allowed when auth.uid() = (SELECT user_id FROM gap_audit_runs WHERE id = artifact_health_scores.audit_run_id). API route handlers re-verify role from profiles after middleware sets x-user-role header; they never trust the header alone -- they re-query Supabase for the session and role before executing any write. Permission checks are enforced in code at the API layer, not solely by RLS, so the gate (F23) and resume (F24) endpoints always do an explicit role assertion before proceeding. No permission is configurable at runtime; the single operator role is hardcoded in the route guards.
